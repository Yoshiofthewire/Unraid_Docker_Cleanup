# Docker Cleanup — Unraid Plugin Design

Date: 2026-08-11
Status: approved for planning

## Purpose

An Unraid plugin that runs `docker image prune -a -f` on a user-controlled
schedule (default: daily at 03:00 local time), and provides a manual,
confirmation-gated button to delete unused Docker volumes.

## Decisions

| Decision | Choice |
|---|---|
| Plugin slug | `docker.cleanup` |
| Settings location | Settings ▸ User Utilities ▸ Docker Cleanup |
| Target Unraid | 6.12 and 7.x |
| Schedule UI | Hourly / Daily / Weekly / Monthly presets + Custom cron |
| Scheduled command | `docker image prune -a -f`, exactly |
| Notifications | On completion, with space reclaimed; warning on failure |
| Volume prune | Preview unused volumes, then `docker volume rm` on precisely the previewed set |
| Manual run | "Run now" button, streams live output |
| Uninstall | Removes cron and plugin files; keeps `.cfg` on flash |
| Tests | Plain-bash test runner with a stub `docker`; lint via Docker containers |
| Packaging | `.plg` + build script + CA template |

## Layout

```

    DockerCleanup.page                        settings page
    include/config.php                        read/write cfg, cron generation, shared helpers
    include/save.php                          POST: save settings, rebuild cron
    include/run.php                           POST: manual image prune, streams output
    include/volumes.php                       GET list unused volumes / POST remove selected
    scripts/image-prune.sh                    what cron runs
    scripts/volume-prune.sh                   removes an explicit list of volumes
    default.cfg
    images/docker-cleanup.png

/boot/config/plugins/docker.cleanup/          flash, survives reboot and reinstall
    docker.cleanup.cfg                        user settings
    docker.cleanup.cron                       generated cron fragment; absent means disabled
    lastrun                                   one line, last result

```

## Configuration

`/boot/config/plugins/docker.cleanup/docker.cleanup.cfg`, `key="value"` form so
PHP `parse_ini_file` and shell `source` both read it.

```
ENABLED="yes"          yes | no
SCHEDULE="daily"       hourly | daily | weekly | monthly | custom
HOUR="3"               0-23
MINUTE="0"             0-59
DAY_OF_WEEK="0"        0-6, weekly only
DAY_OF_MONTH="1"       1-28, monthly only
CUSTOM_CRON=""         5-field cron expression, custom only
NOTIFY="yes"           yes | no
```

Defaults ship in `default.cfg` and are copied to flash on install only when no
config exists. Day of month is capped at 28 so a monthly schedule cannot skip
February.

## Scheduling

Unraid's dynamix convention, not direct crontab editing. The plugin writes a
cron fragment to flash and calls `/usr/local/emhttp/webGui/scripts/update_cron`,
which rebuilds the system crontab from every `/boot/config/plugins/*/*.cron`.

Fragment content:

```
# Generated by the Docker Cleanup plugin — edits are overwritten
0 3 * * * /usr/local/emhttp/plugins/docker.cleanup/scripts/image-prune.sh &>/dev/null
```

Expression per schedule:

| Schedule | Expression |
|---|---|
| hourly | `MINUTE * * * *` |
| daily | `MINUTE HOUR * * *` |
| weekly | `MINUTE HOUR * * DAY_OF_WEEK` |
| monthly | `MINUTE HOUR DAY_OF_MONTH * *` |
| custom | `CUSTOM_CRON` verbatim |

Transitions:

- Save with `ENABLED=yes` — write fragment, run `update_cron`
- Save with `ENABLED=no` — delete fragment, run `update_cron`
- Install or upgrade — regenerate fragment from config, run `update_cron`
- Uninstall — delete fragment, run `update_cron`

Custom cron validation happens before anything is written. The expression must
be exactly five whitespace-separated fields; each field must match
`*`, an integer, a range, a step, or a comma-list of those, with per-field range
checks. Anything containing a newline, `%`, or a shell metacharacter is
rejected. Invalid input produces an error on the page and leaves the existing
cron fragment untouched — a bad expression must never reach the crontab.

## Scheduled image prune

`scripts/image-prune.sh` is run by cron and by the Run Now button. One script,
so a manual test exercises exactly what runs on schedule.

1. `flock` on a lockfile; a second invocation exits immediately rather than
   running concurrently.
2. Guard: if `docker info` fails (array stopped, Docker service disabled), log
   "skipped, Docker not running" and exit 0. This is a normal condition and
   produces no error notification.
3. Run `docker image prune -a -f`.
4. Parse `Total reclaimed space:` from the output.
5. Append the full output to `/var/log/docker-cleanup.log`. If the log exceeds
   1 MB, keep the tail.
6. Write one pipe-delimited line to `/boot/config/plugins/docker.cleanup/lastrun`:
   `2026-08-11T03:00:04-05:00|ok|4509715046|Reclaimed 4.2 GB`. This is one small
   flash write per run, so the settings page can still show the last result
   after a reboot.
7. If `NOTIFY=yes`, call
   `/usr/local/emhttp/webGui/scripts/notify -e "Docker Cleanup" -s <subject> -d <detail> -i <normal|warning>`.
   Success is `normal`; a non-zero exit from Docker is `warning`.

Path constants (`PLUGIN_ROOT`, `BOOT_CONFIG`, `LOG_FILE`, `LOCK_FILE`) default to
the real locations but are overridable by environment variable, so tests run
without root and without touching real paths.

## Volume prune

Never scheduled, never run on install, never run without explicit confirmation.

`docker volume prune` changed behavior in Docker 23: by default it removes only
anonymous unused volumes, and needs `-a` to include named ones. Unraid 6.12 and
7.x ship different Docker versions, so the same command produces different
results across the two targets. The plugin therefore removes an explicit list
rather than invoking `prune`, which guarantees the preview and the action agree
on every Docker version.

Flow:

1. User clicks "Prune unused volumes".
2. `include/volumes.php?action=list` runs
   `docker system df -v --format '{{json .Volumes}}'` and returns every volume
   with `RefCount == 0`, each tagged `anonymous` when the name matches
   `^[0-9a-f]{64}$`, with its size.
3. The dialog lists every unused volume with its size and warns that deletion
   is permanent. Anonymous volumes are selected; named volumes are listed but
   greyed out and excluded until the user ticks "include named volumes", which
   is **unchecked by default**. Only selected volumes are sent in step 4.
4. On confirm, the page POSTs the explicit list of volume names.
5. `include/volumes.php` re-validates before deleting: each name must match
   `^[A-Za-z0-9][A-Za-z0-9_.-]*$`, and must still report `RefCount == 0`. A
   volume that gained a reference between preview and confirm is skipped and
   reported. This closes the window where a container starts mid-dialog.
6. `scripts/volume-prune.sh` runs `docker volume rm -- <names>`, logs the
   result, and the page reports what was removed, what was skipped, and the
   space reclaimed.

## Web UI

`DockerCleanup.page` with `Menu="Utilities"`, `Title="Docker Cleanup"`.

- Enable cleanup: yes/no
- Schedule: preset dropdown; time, day-of-week, day-of-month, and custom cron
  fields show and hide according to the selection
- Notifications: yes/no
- Last run status, read from `lastrun`
- Run now — streams live output
- Prune unused volumes — the flow above

All POST handlers verify the Unraid CSRF token (`$var['csrf_token']`) and
return 403 without it. This is required for every webGui POST.

Live output uses `popen()` with implicit flush and `X-Accel-Buffering: no`,
displayed through the webGui `openBox()` helper. All command output is HTML
escaped before it reaches the page.

## Install and uninstall

`.plg` install script:

- create `/boot/config/plugins/docker.cleanup`
- copy `default.cfg` to flash only when no config exists
- install the `.txz` with `upgradepkg --install-new`
- regenerate the cron fragment from config and run `update_cron`

`.plg` remove script:

- delete the cron fragment, run `update_cron`
- `rm -rf /usr/local/emhttp/plugins/docker.cleanup`
- remove `/var/log/docker-cleanup.log`, the `.txz`, and the `.plg` from flash
- keep `docker.cleanup.cfg` and `lastrun`, so a reinstall restores the schedule

## Verification

`./test` runs everything and is the single entry point.

Lint, through Docker so nothing needs installing on the dev machine:

- `koalaman/shellcheck:stable` over every `.sh`
- `php:8-cli php -l` over every `.php`

Unit tests, plain bash in `tests/run.sh` so the suite itself has no
dependencies. A stub `docker` and stub `notify` are placed on `PATH`; each
records its arguments and returns canned output. Path environment variables
point at a temporary directory.

Coverage:

- correct cron expression for each preset, across boundary values
- malformed custom cron is rejected and leaves the existing fragment intact
- enable, disable, and uninstall each produce the right fragment state and call
  `update_cron`
- image prune invokes exactly `docker image prune -a -f`
- image prune exits 0 and writes a "skipped" record when `docker info` fails
- reclaimed space is parsed correctly, including a zero-reclaim run
- `lastrun` is written and parsed back for display
- notification fires with `normal` on success, `warning` on failure, and not at
  all when `NOTIFY=no`
- the lock prevents a concurrent second run
- volume listing excludes any volume with a non-zero `RefCount`
- volume removal rejects names failing the character check
- volume removal skips a volume whose `RefCount` became non-zero after preview
- every POST handler rejects a request with a missing or wrong CSRF token

## Packaging

`build/build.sh`:

1. stage `plugin/` as `usr/local/emhttp/plugins/docker.cleanup`
2. produce `docker.cleanup-YYYY.MM.DD.txz` and its `.md5`
3. stamp version and md5 into `docker.cleanup.plg`
4. write both to `release/`

Version is date-based, `YYYY.MM.DD`, with a `.N` suffix for a second release in
one day. The `.plg` fetches the `.txz` from a GitHub release.

`ca/docker.cleanup.xml` is the Community Applications template, published from
this repository so edits reach existing installs, matching the pattern in
`Yoshiofthewire/unraid_docker_apps`.

## Out of scope

- container, network, and build-cache pruning
- `docker system prune`
- appdata or log cleanup
- per-image age or retention rules
- any scheduled deletion of volumes

## Risks

- `update_cron` is assumed present at
  `/usr/local/emhttp/webGui/scripts/update_cron` on both 6.12 and 7.x. The
  scripts check for it and fail loudly with a clear message rather than
  silently doing nothing.
- `docker system df -v --format` output shape varies across Docker versions.
  The volume listing parses defensively and reports a clear error rather than
  guessing when the shape is unrecognized.
- At boot, Docker may not be up when cron fires. The `docker info` guard makes
  that a logged skip, not a failure.
